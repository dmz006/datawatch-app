**Filed:** 2026-09-15

## Overview

Three sequential daemon releases expand the memory system from a flat session-local
store to a six-layer scoped hierarchy with full lifecycle controls. BL385 is
foundational (new scopes + endpoints); BL386 adds lifecycle management (seed,
harvest, delete strategy); BL387 extends cross-PRD seeding and adds a UI stats
tile. Work must be done in order: 385 → 386 → 387.

---

## BL385 — Scope model (daemon v8.29.0, GH#174)

### What changed server-side
- Two new scope layers added: **`prd-shared`** (tuple: `(projectDir, "prd/<id>", "")`)
  and **`story-shared`** (tuple: `(projectDir, "story/<id>", "")`).
- Full 6-layer hierarchy (read precedence top → bottom):
  `persona-global → persona-in-project → project-shared → prd-shared → story-shared → session-local`
- New REST endpoints:
  - `POST /api/memory/scopes/save` — write to a named scope
  - `POST /api/memory/scopes/delete` — bulk-delete a scope
  - `GET /api/memory/scopes/recall` — extended: accepts `prd_id` and `story_id` query params
- `GET /api/memory/scopes/recall` response: memory entries now carry `prd_id` and `story_id`
  fields when they were written to a scoped layer.

### Android acceptance criteria
- [ ] Memory objects from `/api/memory/scopes/recall` with `prd_id`/`story_id` fields
      tolerate new additive fields without crash (model already uses `@SerializedName`
      ignore-unknown — verify no `@JsonIgnoreProperties` exclusions needed)
- [ ] `POST /api/memory/scopes/save` callable from any admin/operator path that
      today exposes memory write actions (if any; otherwise no-op until BL386/387 UI)
- [ ] `POST /api/memory/scopes/delete` callable from admin flows
- [ ] Add row to `docs/parity-status.md` memory-scope section:
      `prd-shared / story-shared scope | PWA ✅ | Android ⬜ | iOS ⬜`

### Locale keys needed
None required for BL385 alone (no new UI surfaces; tolerance is backend-only).

## BL386 — Memory lifecycle (daemon v8.30.0, GH#175)

### What changed server-side
New PRD struct fields (additive — old clients must tolerate):
```json
{
  "memory_seed": {
    "enabled": true,
    "max_per_scope": 20,
    "role_filter": ["learning", "decision"],
    "from_archives": [{"prd_id": "...", "role_filter": ["learning"], "max": 20}]
  },
  "memory_harvest": {
    "enabled": true,
    "promote_to": "story-shared",
    "role_filter": ["learning", "decision"],
    "max": 50
  }
}
```
New `memory_strategy` param on PRD delete and session delete:
- `DELETE /api/autonomous/prds/{id}` body: `{"memory_strategy": "archive"|"keep"|"purge", ...}`
- `POST /api/sessions/delete` body: same `memory_strategy` field
New endpoint:
- `POST /api/memory/scopes/archive-import` — seed a new PRD from archived memories
New PRD response fields: `memory_report` (string, nullable) + `memory_report_at` (timestamp)
New endpoint: `GET /api/autonomous/prds/{id}/memory-report`

### Android acceptance criteria

**PRD create/edit screen**
- [ ] Add `memory_seed.enabled` toggle (default off, label: "Seed memory at start")
- [ ] Add `memory_seed.from_archives` multi-select: list completed/archived PRDs in project
      by name; maps to `[{prd_id, role_filter: ["learning","decision"], max: 20}]`
- [ ] Add `memory_harvest.enabled` toggle (default off)
- [ ] Add `memory_harvest.promote_to` picker: session-local / story-shared / prd-shared /
      project-shared (shown when harvest enabled)
- [ ] All new fields sent on PRD create/update; omitted when defaults (no server breakage)

**PRD delete dialog**
- [ ] Extend `DeletePrdDialog` with "Memory strategy" segmented control or radio:
      Keep (default) · Purge · Archive
- [ ] When Archive: show role-filter chip row (Learning / Decision / all) matching PWA
- [ ] `memory_strategy` passed in delete body only when non-default

**Session delete**
- [ ] `SessionDeleteDialog` (or equivalent) passes `memory_strategy` param; same
      Keep/Purge/Archive picker

**PRD detail screen**
- [ ] Render `memory_report` when non-null as a collapsible `MarkdownCard` section
      ("What this PRD learned") after the status/progress block
- [ ] Show `memory_report_at` as "Report generated <date>" subtitle
- [ ] Fetch via `GET /api/autonomous/prds/{id}/memory-report` on-demand (lazy: show
      "Load report" button until tapped; then cache in VM)

## BL387 — PRD memory integration (daemon v8.31–v8.33, GH#176)

### What changed server-side
Phase 1 (v8.31.0): Backend only — no mobile-visible surface.

Phase 2 (v8.32.0): `memory_seed.from_prds` field on PRD create/edit:
```json
{"memory_seed": {"from_prds": ["0fb4e302", "a1b2c3d4"]}}
```
Seeds from live `prd-shared` scopes of listed PRDs at decomposition time (live PRDs,
not archived — distinct from `from_archives` in BL386).

Phase 3 (v8.33.0):
- `memory_report` auto-generated on PRD completion (already covered by BL386 rendering)
- PRD response gains three new count fields: `prd_shared_count`, `story_shared_count`,
  `session_local_count`
- PWA adds a memory stats tile on PRD status card

### Android acceptance criteria

**PRD create/edit screen (Phase 2)**
- [ ] `memory_seed.from_prds` multi-select: lists currently active/running PRDs in the
      same project that have prd-shared memory; label "Seed from active PRDs"; subtitle
      "Inherits learnings from selected PRDs at task start"
- [ ] Distinct from `from_archives` (BL386) — show both when server ≥v8.32.0

**PRD detail/status screen (Phase 3)**
- [ ] Memory stats row in PRD status card when any count > 0:
      `Memory: prd-shared N · story-shared N · session N`
- [ ] Tappable row opens scope inventory view (stretch goal: defer to v9.0.0 timeline
      per issue spec)
- [ ] Counts refresh on pull-to-refresh (already handled by PRD detail refresh)

**Wear/Auto:** No new affordances required per issue spec — memory stats are view-only.

## Implementation order

```
BL385 → BL386 → BL387
```

BL385 is a tolerance pass (no new UI, just DTO tolerance + endpoint wiring).
BL386 is the largest surface (PRD create/edit extensions + delete dialog + detail render).
BL387 builds on BL386's `memory_report` rendering and adds Phase 2/3 fields.

Suggested sprint grouping (TBD):
- Sprint A: BL385 tolerance pass + `prd_shared_count` field tolerance (Phase 3 prep) — small
- Sprint B: BL386 PRD create/edit + delete dialog + memory_report render
- Sprint C: BL387 Phase 2 (`from_prds` multi-select) + Phase 3 (memory stats tile)

## API probe strategy

Server version detection via existing `GET /api/version`. Gate new UI behind:
- BL385 endpoints: `version >= "8.29.0"`
- `from_archives` / harvest / delete strategy: `version >= "8.30.0"`
- `from_prds`: `version >= "8.32.0"`
- Memory count fields: `version >= "8.33.0"`

Existing `ServerProfile.serverVersion` flow already handles version-gated features —
follow the same pattern as UnifiedPush and LLM tier gates.
